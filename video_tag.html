Видеопоток: API

Как подключить камеру и смотреть её в конфигураторе, описано в разделе Подключение видеокамер. Здесь — как получать видео и управлять камерой из своих программ и веб-страниц.

Тег видеопотока — тег с prsValueTypeCode = 6. Вместо ряда чисел он отдаёт медиаданные: живой поток, снимок или запись за период.

Чтение

Видео читается тем же запросом, что и данные обычного тега, GET /v1/data/, но ответ зависит от ключей start и finish:

Запрос

Ответ

без start и finish

Живой поток. Видео передаётся только по WebRTC (см. Живой поток), поэтому на сам GET платформа отвечает ошибкой 404 «Живой поток открывается через WebRTC.». С ключом audio=1 — звук живого потока, audio/mpeg.

только finish

Снимок image/jpeg на этот момент. Для текущего момента кадр берётся из живого соединения, для прошлого — из архива.

start и finish

Запись за период, video/mp4.

Метки start и finish задаются микросекундами или датой ISO 8601, как в запросах исторических данных. В адресе знак + часового пояса кодируется как %2B. Ключи timeStep и count для видео не поддерживаются, в одном запросе читается один тег.

Запись за период не лежит на диске готовым файлом. Сервис захвата находит файлы архива, покрывающие период, склеивает их и перекодирует в один mp4 (H.264). На это отводится до 180 секунд, и всё это время клиент ждёт ответ.

Если записи нет, вместо картинки приходит JSON с ошибкой (см. Ошибки).

Живой поток

Живой поток передаётся по WebRTC. Клиент создаёт RTCPeerConnection на приём видео и отправляет предложение SDP на POST /v1/video/webrtc:

{"tagId": "<id тега>", "sdp": "<SDP offer>", "type": "offer"}

Платформа проверяет право чтения тега и возвращает ответ SDP:

{"sdp": "<SDP answer>", "type": "answer"}

Само видео идёт на порт 8189 (UDP и TCP) того же сервера, с которого открыта страница: nginx принимает его и передаёт сервису захвата. Видео — H.264 профиля Baseline, 15 кадров в секунду, ширина 960 пикселей, без звука. Поток кодируется один раз на камеру, и все зрители получают одну и ту же копию.

Звук живого потока, если он есть у камеры, читается отдельно: GET /v1/data/?tagId=<id>&audio=1 возвращает audio/mpeg. Если звука в потоке нет, ответ — 404.

Своя страница

Страницу с видео размещают на том же сервере, что и платформу: адреса /v1/data/ и /v1/video/webrtc уже обслуживает nginx. Если включена авторизация, браузер подставит в запросы только куки этого сервера — ещё одна причина держать страницу на нём.

Живой поток со звуком:

<video id="cam" autoplay muted playsinline></video>
<audio autoplay
       src="/v1/data/?tagId=67bde18c-5431-1041-925c-470278307e33&amp;audio=1">
</audio>

<script>
const tagId = "67bde18c-5431-1041-925c-470278307e33";
const video = document.getElementById("cam");
const pc = new RTCPeerConnection({iceServers: []});
pc.addTransceiver("video", {direction: "recvonly"});
pc.ontrack = (ev) => { video.srcObject = ev.streams[0]; };

pc.createOffer()
  .then((offer) => pc.setLocalDescription(offer).then(() => offer))
  .then((offer) => fetch("/v1/video/webrtc", {
    method: "POST",
    headers: {"Content-Type": "application/json"},
    body: JSON.stringify({tagId, sdp: offer.sdp, type: offer.type}),
  }))
  .then((res) => res.json())
  .then((answer) => pc.setRemoteDescription(answer));

// чтобы закрыть просмотр: pc.close(); архив продолжит писаться
</script>

Снимок на момент:

<img alt="Снимок"
     src="/v1/data/?tagId=67bde18c-5431-1041-925c-470278307e33&amp;finish=2026-10-05T18:36:20%2B03:00">

Запись за период. Картинка появится после того, как платформа соберёт mp4:

<video controls
       src="/v1/data/?tagId=67bde18c-5431-1041-925c-470278307e33&amp;start=2026-10-05T18:36:00%2B03:00&amp;finish=2026-10-05T18:37:00%2B03:00">
</video>

Если записи нет, сервер отвечает JSON, и элемент img или video останется пустым. Текст ошибки можно получить отдельным fetch по тому же адресу.

Если перед платформой стоит свой прокси, отключите для /v1/data/ буферизацию ответа: иначе звук и длинные ответы будут приходить с большой задержкой.

Управление камерой

Поворот, зум и настройки изображения — запрос POST /v1/ptz/ с телом JSON. Обязательные поля — tagId тега видеопотока и action:

action

Что делает

status

Текущее положение (pan, tilt, zoom), профиль и список предустановок. То же возвращает GET /v1/ptz/?tagId=<id>.

move

Непрерывное движение, пока не придёт stop или не пройдут 8 секунд. Поля pan, tilt, zoom — скорость от −1 до 1. Повтор той же команды во время движения на камеру не отправляется.

step

Один относительный сдвиг на pan, tilt, zoom.

pulse

Один шаг зума; направление задаёт знак zoom.

stop

Остановить поворот и наклон.

home

Вернуть камеру назад по движениям, отправленным с момента запуска сервиса захвата, затем перейти в домашнее положение камеры.

preset

Перейти к предустановке; её идентификатор — в поле token или preset.

image

Текущие настройки изображения и допустимые значения.

image_set

Изменить настройки: brightness, contrast, saturation, sharpness (числа), backlight и wideDynamicRange (ON / OFF), irCut (ON / OFF / AUTO), whiteBalance (AUTO / MANUAL).

Пример:

{"tagId": "<id тега>", "action": "move", "pan": 0.5, "tilt": 0, "zoom": 0}

Если камера объявляет шкалу скорости больше 1, перед первым движением платформа выставляет максимальную скорость, иначе объектив еле ползёт.

Ошибки управления: тег не видеопотока — 422, тег выключен — 409, тег не привязан к камере — 424, камера отклонила команду — 502.

Ошибки

Ошибка приходит JSON вида {"error": {"code": ..., "message": "..."}}, а не картинкой.

  • 404 «Нет записи камеры на этот момент.» — на finish нет файла архива.

  • 404 «Нет записи камеры за этот период.» — между start и finish нет файлов архива.

  • 404 «Живой поток открывается через WebRTC.» — GET без start и finish; используйте POST /v1/video/webrtc.

  • 409 «Тег видеопотока выключен.»

  • 422 «Видеопоток читается по одному тегу за запрос.»

  • 422 «Для видеопотока ключи timeStep и count пока не поддерживаются.»

  • 422 «В периоде видеопотока finish должен быть позже start.»

  • 422 «Слишком длинный видеофрагмент.» — период длиннее VIDEO_MAX_FRAGMENT_SECONDS (по умолчанию 7200 секунд).

  • 422 «Звук камеры есть только у живого потока.» — audio=1 вместе с start или finish.

  • 424 «Тег видеопотока не привязан к активному коннектору-камере.»

  • 424 «Тег видеопотока не привязан к хранилищу видео.»

  • 502 — камера не отдала кадр или не удалось собрать видеофайл.

  • 503 «Не найден ffmpeg.»

  • 503 «Сервис отдачи видео не запущен.»

  • 503 «Сервис подхвата видео не запущен.»

Устройство видеосервисов

Этот раздел нужен администраторам, которые распределяют камеры между несколькими серверами.

Захват (prs-video-capture) держит соединение RTSP с камерой, пишет архив, управляет камерой по OnVif и открывает в брокере MQTT-сессию с ClientId камеры, по которой конфигуратор показывает состояние связи. Отдача (prs-video-delivery) принимает запросы чтения тегов и забирает данные у захвата по HTTP внутри сети Docker. По RabbitMQ передаются только адреса сервисов, сами кадры через брокер не идут.

Какие камеры обслуживает процесс захвата и какие теги — процесс отдачи, задаёт список nodes в настройках процесса. Пустой список означает «все». Одну камеру должен обслуживать ровно один процесс захвата: два процесса откроют к камере два соединения. Поэтому либо запускают один процесс с пустым nodes, либо несколько процессов с непересекающимися списками.

Платформа находит нужный процесс запросами video.delivery.locate.<id тега> и video.capture.lookup.<id коннектора>; процесс отвечает своим адресом (настройка http_base_url).

Распознавание берёт кадры из того же соединения с камерой и второе соединение не открывает.

Сервис захвата ставит каждому кадру метку времени прихода на сервер. Кадры, пришедшие ближе 20 мс к предыдущему, считаются одним кадром. Это защищает от камер, которые неправильно ведут счётчик времени RTSP: ffmpeg принимает их поток за 90 000 кадров в секунду, архив раздувается, а живой просмотр почти не получает кадров.
