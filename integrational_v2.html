Интеграционные хранилища

Обычное хранилище данных само создаёт таблицы и хранит в них историю тегов в своём формате. Но часто данные уже лежат во внешней базе: справочники, планы, календари, заказы из ERP. Чтобы не копировать их в платформу, используют интеграционное хранилище. Тег, привязанный к нему, читает и пишет значения не в служебную таблицу, а запросами SQL к внешней базе. Эти запросы называются операциями.

Клиент работает с таким тегом обычными запросами GET /v1/data/ и POST /v1/data/, а платформа выполняет за него нужную операцию.

Включение

Интеграционные хранилища используют API версии 2. В стандартной поставке он включён переменной PRS_ENABLE_V2=1 в docker/compose/.cont_one_app.env. Значения 1, true, yes, on включают API v2, пустое значение оставляет только v1.

MCP-сервер платформы показывает инструменты v2, если задана переменная MCP_PERESVET_ENABLE_V2=1; если она не задана, берётся значение PRS_ENABLE_V2 (см. MCP-сервер платформы).

Хранилище

Интеграционное хранилище — узел prsDataStorage с кодом типа prsEntityTypeCode = 2. Адрес внешней базы PostgreSQL задаётся ключом dsn в конфигурации хранилища:

{"dsn": "postgresql://user:password@erp-db:5432/erp"}

Сервер платформы должен иметь сетевой доступ к этой базе.

Тег и операции

Тег становится интеграционным, когда его привязывают к интеграционному хранилищу. У привязки есть операции — именованные запросы SQL двух видов:

  • GET (prsEntityTypeCode = 0) — чтение значений тега;

  • SET (prsEntityTypeCode = 1) — запись значений тега.

У каждой операции есть параметры. Параметр соответствует подстановке :имя в тексте запроса, а его значение вычисляется выражением JSONata из запроса клиента.

В конфигураторе операции задают в параметрах привязки тега к хранилищу (папка «Хранилища данных», щелчок по привязке). В LDAP операция — дочерний узел prsDatastorageTagOperation под узлом привязки prsDatastorageTagData, параметр — узел prsDatastorageTagOperationParameter под операцией.

Конфигурация операции

В prsJsonConfigString операции:

Ключ

Смысл

query

Текст запроса SQL с именованными параметрами :имя. Обязателен.

timeoutMs

Ограничение времени выполнения, мс.

maxRows

Наибольшее число строк результата.

version

Номер версии операции, для вашего учёта.

Ограничения запроса: одна команда SQL (символ ; запрещён), команды изменения структуры базы (CREATE, ALTER, DROP, TRUNCATE и т.п.) запрещены.

Запрос GET-операции должен вернуть колонки x (метка времени), y (значение) и q (код качества). Платформа превратит строки результата в обычный ответ исторических данных:

{"data": [{"tagId": "<id тега>", "data": [["<x1>", "<y1>", "<q1>"], ["<x2>", "<y2>", "<q2>"]]}]}

Параметры операции

  • Для каждой подстановки :имя в запросе должен быть параметр с cn, равным имя, и выражением JSONata в ключе JSONata его prsJsonConfigString.

  • Значений по умолчанию нет. Если параметр не описан или выражение вернуло null, запрос завершается ошибкой.

Выражение JSONata вычисляется над объектом, в котором есть:

  • все ключи запроса клиента (start, finish, tagId и т.д.);

  • params — объект с дополнительными параметрами, которые клиент передал в запросе;

  • для SET-операции — ещё x, y, q текущей записываемой точки. SET-операция выполняется отдельно для каждой точки.

Пример привязки

Тег читает заказы ERP за период и удаляет заказ по метке времени. Запрос PUT /v2/dataStorages:

{
  "id": "<id хранилища>",
  "linkedTags": [
    {
      "tagId": "<id тега>",
      "operations": [
        {
          "attributes": {
            "cn": "erp.orders.select",
            "prsEntityTypeCode": 0,
            "prsDefault": true,
            "prsJsonConfigString": {
              "query": "select ts as x, payload as y, 0 as q from erp_orders where ts >= :start and ts < :finish order by ts",
              "timeoutMs": 5000,
              "maxRows": 10000
            }
          },
          "parameters": [
            {"attributes": {"cn": "start",  "prsJsonConfigString": {"JSONata": "$.start"}}},
            {"attributes": {"cn": "finish", "prsJsonConfigString": {"JSONata": "$.finish"}}}
          ]
        },
        {
          "attributes": {
            "cn": "erp.orders.delete",
            "prsEntityTypeCode": 1,
            "prsDefault": true,
            "prsJsonConfigString": {
              "query": "delete from erp_orders where ts = :x",
              "timeoutMs": 5000
            }
          },
          "parameters": [
            {"attributes": {"cn": "x", "prsJsonConfigString": {"JSONata": "$.params.x"}}}
          ]
        }
      ]
    }
  ]
}

Узел привязки получает имя, равное tagId; задавать attributes привязки не обязательно.

Выбор операции

Какую операцию выполнить, клиент указывает ключом operation:

  • в GET /v1/data/ — параметр запроса operation с cn GET-операции;

  • в POST /v1/data/ — поле operation у элемента data[i] с cn SET-операции.

Если operation не указан:

  • операция нужного вида у тега одна — выполняется она;

  • таких операций несколько — выполняется та, у которой prsDefault = true;

  • операций с prsDefault = true несколько или нет ни одной — ошибка.

В конфигураторе первая созданная операция каждого вида сразу получает prsDefault = true.

Примеры запросов клиента

Чтение за сутки операцией по умолчанию:

{
  "tagId": ["<id тега>"],
  "start": "2026-02-02T00:00:00+03:00",
  "finish": "2026-02-03T00:00:00+03:00"
}

Удаление заказа операцией erp.orders.delete. Значение x передаётся в params, потому что выражение параметра ссылается на $.params.x:

{
  "data": [
    {
      "tagId": "<id тега>",
      "data": [],
      "operation": "erp.orders.delete",
      "params": {"x": 1738450800000}
    }
  ]
}

API v2 хранилищ данных

В API v2 операции передаются внутри linkedTags: поле linkedTags[].operations, а у операции — parameters.

  • GET /v2/dataStorages — чтение; операции возвращаются по флагу запроса;

  • POST /v2/dataStorages — создание вместе с операциями. parentId может указывать на пользовательскую папку в ветке хранилищ;

  • PUT /v2/dataStorages — изменение вместе с операциями.

Параметры GET-запросов (id, base, scope, filter и т.д.) рекомендуется передавать обычными параметрами адреса, а не одной строкой q=<json>.
