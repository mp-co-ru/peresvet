Коннекторы
==========

Коннектор — программа, которая читает данные внешнего источника и передаёт
их в теги платформы. Источником может быть контроллер, прибор, промышленная
шина, база данных — всё, к чему есть протокол.

Обычно один коннектор работает с одним источником по одному протоколу:
Modbus, OPC, собственный протокол прибора. Если одинаковых приборов
несколько, запускают несколько копий одной программы. У каждой копии свой
узел в платформе и свой файл настроек.

Платформа хранит описание коннектора и список привязанных к нему тегов.
Сам коннектор работает рядом с источником, сам опрашивает его и передаёт
значения в платформу по протоколу MQTT.

Где запускать
-------------

Коннектор ставят как можно ближе к источнику: на компьютер в цеху,
на шлюз рядом с контроллером, на машину, к которой подключён
последовательный порт.

Тогда опрос прибора, самый капризный участок, остаётся локальным, а до
платформы данные идут по MQTT, и сеть там может быть длиннее и хуже.
Если связь с платформой пропала, коннектор складывает значения в файл
буфера на своей машине и передаёт их после восстановления связи,
с исходными метками времени.

Как это работает
----------------

#. В конфигураторе в папке «Коннекторы» создают узел коннектора.
   В его конфигурации два блока: ``source`` — как подключиться к источнику
   (формат задаёт конкретный коннектор) и ``log`` — настройки журнала.
#. К коннектору привязывают теги. У каждой привязки свои параметры:
   адрес значения в источнике, выражение JSONata для преобразования,
   значимое отклонение и период опроса.
#. На машине коннектора лежит короткий файл настроек: идентификатор узла
   коннектора в платформе и адрес MQTT. Всю остальную конфигурацию коннектор
   получает от платформы и сохраняет у себя на диске. Поэтому изменения,
   сделанные в конфигураторе, доходят до работающего коннектора без правки
   файлов на его машине.
#. Коннектор подключается к платформе по MQTT и запрашивает конфигурацию.
   Получив её, он опрашивает источник и присылает текущие значения всех
   привязанных тегов.
#. Каждое прочитанное значение проходит выражение JSONata, приводится к типу
   тега и сравнивается с последним отправленным. Если разница меньше
   значимого отклонения (``maxDev``), значение не отправляется. Если связи
   с платформой нет, значение пишется в буфер.

Видеокамера — тоже коннектор, но её обслуживает сама платформа,
см. :ref:`video_cameras`.

Потеря и восстановление связи
-----------------------------

Платформа следит за связью с каждым коннектором и отмечает её изменения
в истории тегов. Это позволяет отличить «значение не менялось» от «данных
не было, потому что не было связи».

* Когда связь с коннектором пропадает, платформа записывает во все его теги
  значение ``null`` с кодом качества **100**.
* Когда коннектор снова подключается и запрашивает конфигурацию, платформа
  записывает во все его теги ``null`` с кодом качества **101** и только
  после этого отправляет конфигурацию.

Коды качества описаны в разделе :ref:`qualityCodes`.

После обрыва связи история тега выглядит так:

#. ``null`` с качеством 100 — момент потери связи;
#. значения из буфера коннектора, накопленные без связи, — с их исходными
   метками времени;
#. ``null`` с качеством 101 — момент восстановления связи;
#. текущие значения из источника, прочитанные после получения конфигурации.
   Коннектор присылает их, даже если они не изменились, поэтому текущее
   значение тега не остаётся ``null``.

Журнал
------

Коннектор всегда пишет журнал в файл на своей машине. Имя файла, уровень
подробности, размер файла и число архивных копий задаются в блоке ``log``
конфигурации.

Если в конфигураторе включён флажок **Лог в платформу**, те же строки
передаются в платформу, и их видно на вкладке **Лог коннектора**.
Вывод удалённых команд в этот журнал не попадает, он показывается
отдельно (см. `Удалённые команды`_).

По этим сообщениям журнала видно, что происходит с коннектором. Перед
текстом в журнале стоит уровень (``INFO``, ``WARNING``, ``ERROR``).

.. list-table::
   :header-rows: 1
   :widths: 48 52

   * - Сообщение
     - Что произошло
   * - ``Подключение к брокеру MQTT платформы ...``
     - Коннектор пытается подключиться к платформе.
   * - ``Связь с платформой установлена.``
     - Подключение есть. Следом коннектор запросит конфигурацию.
   * - ``Разрыв связи с платформой: ...``
     - Связь потеряна. Новые значения пишутся в буфер.
   * - ``Сообщение от платформы: prsConnector.full_configuration.``
     - Пришла полная конфигурация. После первой такой конфигурации
       в сеансе связи коннектор читает все привязанные теги.
   * - ``Сообщение от платформы: prsConnector.connector_configuration.``
     - Изменились параметры самого коннектора: источник, журнал или
       признак активности.
   * - ``Конфигурация коннектора изменена.``
     - Новые параметры коннектора приняты.
   * - ``Сообщение от платформы: prsConnector.tags_configuration.``
     - Добавлен тег или изменена привязка тега.
   * - ``Конфигурация тегов изменена.``
     - Новый список тегов принят, опрос перезапущен.
   * - ``Тег <id> удалён из списка.``
     - Тег отвязан от коннектора.
   * - ``Конфигурация сохранена.``
     - Конфигурация записана на диск коннектора.
   * - ``Коннектор активен, работа по чтению данных запущена.``
     - Узел коннектора включён, опрос источника идёт.
   * - ``Коннектор неактивен, работа по чтению данных остановлена.``
     - Узел коннектора выключен. Коннектор остаётся на связи и ждёт
       новую конфигурацию.
   * - ``Отправка данных в платформу.``
     - Накопленные значения отправлены в платформу.
   * - ``Данные сохранены в буфер.``
     - Связи нет, значение сохранено в файле буфера.
   * - ``Ошибка передачи данных: сохраняем в буфер.``
     - Отправка не удалась, значение сохранено в буфер.
   * - ``Обработка буфера данных.``
     - Связь есть, значения из буфера снова отправляются.
   * - ``Тег '<id>'. Ошибка конвертации значения ...``
     - Значение из источника не удалось привести к типу тега.
   * - ``Неверная конфигурация тега <id>.``
     - Не удалось разобрать привязку тега, тег не опрашивается.
   * - ``Очередь сообщений переполнена.``
     - Отправка не успевает за опросом, часть буфера отложена.
   * - ``Получен сигнал завершения работы, сохраняем данные...``
     - Коннектор останавливается и сохраняет буфер на диск.
   * - ``Работа коннектора завершена.``
     - Коннектор остановлен.

Удалённые команды
-----------------

Коннектору можно отправить команды оболочки, которые он выполнит на своей
машине: например, проверить сеть до прибора или посмотреть файлы.
В конфигураторе это вкладка **Команды коннектору**: каждая непустая строка —
отдельная команда. Через API — запрос ``POST /v1/connectors_app/``:

.. code-block:: json

   {
     "id": "<id коннектора>",
     "command": {"lines": ["ping -c 3 192.168.1.50", "df -h"]}
   }

Необязательные поля ``command``: ``timeoutSec`` — ограничение времени
на одну строку (по умолчанию 120 секунд), ``maxOutputBytes`` — сколько байт
вывода сохранять (по умолчанию 65536), ``logToPlatform`` — включить или
выключить передачу журнала в платформу.

Результат каждой команды (код выхода и вывод) коннектор возвращает
в платформу. Последние результаты отдаёт запрос
``GET /v1/connectors_app/command_output_tail?id=<id коннектора>``.

.. warning::

   Команды выполняются на машине коннектора с правами его процесса.
   В открытой редакции платформа не проверяет, кто отправляет команду,
   поэтому не открывайте API платформы в недоверенную сеть.

Свой коннектор
--------------

Общая часть всех коннекторов вынесена в Python-пакет
`prs-connector-core <https://github.com/mp-co-ru/prs-connector-core>`__.
Его главный класс — ``BaseConnector``.

Базовый класс сам подключается к платформе по MQTT, запрашивает и применяет
конфигурацию, хранит её на диске, применяет JSONata, приводит типы,
проверяет значимое отклонение, ведёт буфер, сообщает платформе о потере
связи и пишет журнал. В наследнике остаётся только чтение источника:
забрать значения и положить их в очередь.

В конфигурации коннектора ключ ``source`` описывает подключение к прибору,
в привязке тега свой ключ ``source`` описывает, как прочитать этот тег.
Формат обоих задаёт автор коннектора.

Порядок разработки описан в документации ``prs-connector-core``,
протокол обмена с платформой — в разделе :doc:`connectors` справочника API.
