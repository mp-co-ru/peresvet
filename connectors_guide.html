Коннекторы

Коннектор — программа, которая читает данные внешнего источника и передаёт их в теги платформы. Источником может быть контроллер, прибор, промышленная шина, база данных — всё, к чему есть протокол.

Обычно один коннектор работает с одним источником по одному протоколу: Modbus, OPC, собственный протокол прибора. Если одинаковых приборов несколько, запускают несколько копий одной программы. У каждой копии свой узел в платформе и свой файл настроек.

Платформа хранит описание коннектора и список привязанных к нему тегов. Сам коннектор работает рядом с источником, сам опрашивает его и передаёт значения в платформу по протоколу MQTT.

Где запускать

Коннектор ставят как можно ближе к источнику: на компьютер в цеху, на шлюз рядом с контроллером, на машину, к которой подключён последовательный порт.

Тогда опрос прибора, самый капризный участок, остаётся локальным, а до платформы данные идут по MQTT, и сеть там может быть длиннее и хуже. Если связь с платформой пропала, коннектор складывает значения в файл буфера на своей машине и передаёт их после восстановления связи, с исходными метками времени.

Как это работает

  1. В конфигураторе в папке «Коннекторы» создают узел коннектора. В его конфигурации два блока: source — как подключиться к источнику (формат задаёт конкретный коннектор) и log — настройки журнала.

  2. К коннектору привязывают теги. У каждой привязки свои параметры: адрес значения в источнике, выражение JSONata для преобразования, значимое отклонение и период опроса.

  3. На машине коннектора лежит короткий файл настроек: идентификатор узла коннектора в платформе и адрес MQTT. Всю остальную конфигурацию коннектор получает от платформы и сохраняет у себя на диске. Поэтому изменения, сделанные в конфигураторе, доходят до работающего коннектора без правки файлов на его машине.

  4. Коннектор подключается к платформе по MQTT и запрашивает конфигурацию. Получив её, он опрашивает источник и присылает текущие значения всех привязанных тегов.

  5. Каждое прочитанное значение проходит выражение JSONata, приводится к типу тега и сравнивается с последним отправленным. Если разница меньше значимого отклонения (maxDev), значение не отправляется. Если связи с платформой нет, значение пишется в буфер.

Видеокамера — тоже коннектор, но её обслуживает сама платформа, см. Подключение видеокамер.

Потеря и восстановление связи

Платформа следит за связью с каждым коннектором и отмечает её изменения в истории тегов. Это позволяет отличить «значение не менялось» от «данных не было, потому что не было связи».

  • Когда связь с коннектором пропадает, платформа записывает во все его теги значение null с кодом качества 100.

  • Когда коннектор снова подключается и запрашивает конфигурацию, платформа записывает во все его теги null с кодом качества 101 и только после этого отправляет конфигурацию.

Коды качества описаны в разделе Коды качества.

После обрыва связи история тега выглядит так:

  1. null с качеством 100 — момент потери связи;

  2. значения из буфера коннектора, накопленные без связи, — с их исходными метками времени;

  3. null с качеством 101 — момент восстановления связи;

  4. текущие значения из источника, прочитанные после получения конфигурации. Коннектор присылает их, даже если они не изменились, поэтому текущее значение тега не остаётся null.

Журнал

Коннектор всегда пишет журнал в файл на своей машине. Имя файла, уровень подробности, размер файла и число архивных копий задаются в блоке log конфигурации.

Если в конфигураторе включён флажок Лог в платформу, те же строки передаются в платформу, и их видно на вкладке Лог коннектора. Вывод удалённых команд в этот журнал не попадает, он показывается отдельно (см. Удалённые команды).

По этим сообщениям журнала видно, что происходит с коннектором. Перед текстом в журнале стоит уровень (INFO, WARNING, ERROR).

Удалённые команды

Коннектору можно отправить команды оболочки, которые он выполнит на своей машине: например, проверить сеть до прибора или посмотреть файлы. В конфигураторе это вкладка Команды коннектору: каждая непустая строка — отдельная команда. Через API — запрос POST /v1/connectors_app/:

{
  "id": "<id коннектора>",
  "command": {"lines": ["ping -c 3 192.168.1.50", "df -h"]}
}

Необязательные поля command: timeoutSec — ограничение времени на одну строку (по умолчанию 120 секунд), maxOutputBytes — сколько байт вывода сохранять (по умолчанию 65536), logToPlatform — включить или выключить передачу журнала в платформу.

Результат каждой команды (код выхода и вывод) коннектор возвращает в платформу. Последние результаты отдаёт запрос GET /v1/connectors_app/command_output_tail?id=<id коннектора>.

Предупреждение

Команды выполняются на машине коннектора с правами его процесса. В открытой редакции платформа не проверяет, кто отправляет команду, поэтому не открывайте API платформы в недоверенную сеть.

Свой коннектор

Общая часть всех коннекторов вынесена в Python-пакет prs-connector-core. Его главный класс — BaseConnector.

Базовый класс сам подключается к платформе по MQTT, запрашивает и применяет конфигурацию, хранит её на диске, применяет JSONata, приводит типы, проверяет значимое отклонение, ведёт буфер, сообщает платформе о потере связи и пишет журнал. В наследнике остаётся только чтение источника: забрать значения и положить их в очередь.

В конфигурации коннектора ключ source описывает подключение к прибору, в привязке тега свой ключ source описывает, как прочитать этот тег. Формат обоих задаёт автор коннектора.

Порядок разработки описан в документации prs-connector-core, протокол обмена с платформой — в разделе Коннекторы справочника API.
